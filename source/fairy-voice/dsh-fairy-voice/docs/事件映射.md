# 事件 → 音效映射

本表是**唯一的行为规格**。左列是 DSH 里真实存在的事件，右列是 `assets/sounds/` 里的素材。
实现见 `lib/client.js` 的 `createDetectors()` / `routeEvent()`。

> **信号原则**：检测层**不在 React 里**，全部来自宿主已公开的**类型化投影与结构化事件**。
> 本插件**一个 DOM 选择器都没用** —— 不是懒，是因为官方 UI 的 DOM 契约里有相当一部分是
> **本地化文本**（`aria-label`、按钮文案），换语言就碎；而事件窗口里的 `reason.kind`
> 是结构化的，换版式不受影响。

---

## 一、主信号源

| 源 | 覆盖 | 形态 |
|---|---|---|
| `ctx.sessions.list` | welcome / session-switch / new-session / goodbye | `ObservableSnapshot<SessionListState>`，`byId[id].blank` 区分新会话 |
| `binding(id).eventSource` | task-start / success / aborted / error / retry / compact-* / model-switch | `ObservableSnapshot<SessionEventWindow>`，**只处理 `change.kind === 'append'` 的增量** |
| `binding(id).session.projections.faceOf('contextPressure')` | context-warning | `{ projectedTokens, pressureTokens, contextWindow }` |
| `ctx.uiSession.pendingInteractions` | permission / permission-approved / permission-denied | `HostObservable<Map<SessionId, PendingApproval>>`，**值是完整对象**，含 `kind` / `key` / `toolName` / `result` |
| `ctx.remote.$on('approval/request')` | permission（**兜底**） | 授权瀑布流。正常路径下**不会被调用**，见下方说明 |
| `ctx.remote.$on('api-session/removed' / 'api-session/error')` | goodbye / error | 会话级 |
| `ctx.connection.generation` | network-error | 掉线即触发 |
| `window.dshDesktop.refreshBalance()` + `dsh-balance-changed` | quota-warning | 桌面壳的桥 |

### 为什么权限**不**以瀑布流为主信号

`dsh-client-ui-approval` 用 `ctx.remote.$on('approval/request', ...)` 接管授权请求，而它
**只在「没有当前会话」或「委托异常」时才调用 `next()`**：

```js
// dsh-client-ui-approval/lib/client.js:235-253
async function answerApproval(ctx, owner, request, next, registerPendingInteraction) {
  if (sessionId === void 0) return next();
  ...
  if (pending.isDelegation(error)) return await next();
```

它是先注册的那个，所以瀑布流到我这里之前就被截断了 —— **把它当主信号是错的**
（本插件早期版本就犯过这个错，置信度标成了「高」，实际根本不会触发）。

正确的主信号是官方自己注册进会话层的 `PendingApproval`。`publishPendingInteractions()`
把**完整交互对象**放进快照表（不是裁过的投影）：

```js
// dsh-client-ui-session/lib/client.js:223
const projected = new Map([...next].map(([sessionId, value]) => [sessionId, value.interaction]));
```

于是请求与决策都能拿到，且不碰瀑布流、不读 DOM、不受界面语言影响。
瀑布流监听器仍然保留（且仍然无条件调用 `next()`），只为覆盖「宿主没装授权界面」的情况。

### 为什么只认 `append`

事件窗口的 `change` 字段带增量语义：
`replace` 是首屏历史、`prepend` 是向前翻页、**只有 `append` 是刚刚发生的**。
不做这个区分的话，打开一个旧会话会把整段历史当成刚发生的事，凭空响一串。

## 二、逐条映射

| 触发器 | 素材 | 精确信号 | 置信度 |
|---|---|---|---|
| `welcome` | welcome-1..7 | `sessions.list.current` 由 `undefined` 变为真实会话 id | **高** |
| `goodbye` | goodbye-1..6 | `current` 变为 `undefined`，或 `api-session/removed`，或 `pagehide` | **中高**（`pagehide` 分支受浏览器限制，可能来不及播完） |
| `task-start` | task-start-1..4 | 事件 `turn/start` | **高** |
| `success` | success-1..3 | 事件 `turn/end` 且 `reason.kind === 'completed'` | **高** |
| `aborted` | aborted.wav | `turn/end` 且 `reason.kind === 'aborted'`；`reason.reason` 存在时仅认 `kind === 'user'`（只对人工停止出声，父级/钩子/销毁导致的中断不打扰） | **高** |
| `error` | error.wav | `turn/end` 且 `reason.kind === 'error'`，`reason.error` 未命中网络特征；或 `reason.kind === 'max-tokens'`；或 `api-session/error` | **高** |
| `network-error` | network-error.wav | `reason.error` 命中网络特征（network/timeout/socket/econn/5xx…）；或 `connection.generation` 掉线 | **高** |
| `retry` | retry.wav | 事件 `llm/retry` | **高** |
| `new-session` | new-session.wav | `current` 变到另一个 id，且 `byId[id].blank === true` | **中高**（宿主按设计复用同一工作区的空白会话，「新建」与「切到一个从未用过的空会话」在信号上难以区分） |
| `session-switch` | session-switch.wav | `current` 在两个真实 id 之间变化（`blank !== true`） | **高** |
| `model-switch` | model-switch.wav | 事件 `model/selection` 在基线之后再次出现 | **中高**（该事件是 log-only 的，首帧为基线，之后每变一次响一次） |
| `permission` | permission-1..3 | `pendingInteractions` 里出现新交互（按 `key` 去重）。**任何阻塞式弹窗**都算 —— 授权、提问、计划确认都走同一张表 | **高** |
| `permission-approved` | permission-approved.wav | 该交互的 `result` promise resolve 成 `'allowed-once'` | **高** |
| `permission-denied` | permission-denied.wav | `result` promise resolve 成 `'rejected'` | **高** |
| `context-warning` | context-warning.wav | `contextPressure` 的 `projectedTokens ?? pressureTokens` 除以 `contextWindow` 越过阈值（默认 80%）；**回落到阈值下 5 个百分点才重新武装** | **高** |
| `quota-warning` | quota-warning.wav | 桌面桥返回的 CNY 余额低于阈值；10 分钟内不重复 | **中高**（无桌面桥时只能等 `dsh-balance-changed`） |
| `compact-auto` | compact-auto.wav | 事件 `compaction/start`，且无 `sourceCommandId`、`turn != null` | **高** |
| `compact-manual` | compact-manual.wav | 事件 `compaction/start`，且有 `sourceCommandId` 或 `turn == null` | **高** |
| `compact-success` | compact-success.wav | 事件 `compaction/summary`，或 `compaction/end` 无 `error` | **高** |
| `compaction-failed` | compaction-failed.wav | 事件 `compaction/end` 带 `error` | **高** |
| `activity` | activity-1..3 | 插件自己的定时器（默认 60 分钟），**默认关闭** | **高**（宿主确实没有这个信号，只能自建） |
| `input` | input.wav | **未接线**：上游 `modules/voice/README.md` 只把它列进文件表，正文未说明用途。开关保留，默认关 | — |
| `voice-on` / `voice-off` | voice-on / voice-off | 用户拨动开关本身，**无视静音** | **高** |

### 权威性说明

- **回合收尾只用 `turn/end`**，不用「最后一个 settled 的 assistant-step」。
  一个回合里搜索、思考、工具调用各自都会 settle，把最后 settle 的那个当成答案会误报。
  `turn/end` 是回合边界的权威事实，且它把 `completed / aborted / error` 结构化地分开了 ——
  不需要靠猜。这正是本插件与 `dsh-fairy-voice` 的关键差别：**原插件得从 chat 节点里推断，
  这里直接读结论**。
- **`reason.kind` 的 `blocked` / `interrupted` 一律不响**。前者是宿主主动拦截，
  后者是崩溃恢复补写的标记，都不是「刚发生的事」。
- **终局互斥**照搬 pi-fairy：`network-error > error > aborted > success`。
  由于 `turn/end` 自带 reason，一个回合只会产生一条终局事件，互斥天然成立。

## 三、未接线与已知偏差

| 项 | 状态 | 说明 |
|---|---|---|
| `input.wav` | **未接线** | 上游 `modules/voice/README.md` 只把它列进文件表，正文没有说明用途 |
| `permission` 的覆盖范围 | 偏宽 | 走的是「任何待处理交互」的表，所以提问、计划确认这类阻塞弹窗也会响。这是照 pi-fairy「Permission phase and other blocking UI prompts」的原意做的；不想要就把这条关掉 |
| 多弹窗同时出现 | 只响一个 | 快照表按 sessionId 只保留**优先级最高**的那一个交互，同会话并存两个弹窗时只会看到最上面的 |
| `model-switch` 首帧 | 只记录不响 | 打开会话时历史走 `replace`，所以第一帧是基线；之后的 `model/selection` 才是真实切换 |
| `new-session` vs 空白会话 | 可能归类错 | 宿主刻意复用同一工作区的空白会话（`service.d.ts` 明确写了），信号上无法完全区分 |
| 后台会话的回合事件 | **不可用** | 事件窗口只对**在台上**（current）的会话开放。后台会话只暴露粗粒度的 `running` 布尔 |
| DSH 关闭 | 只能尽力 | 没有 API。`pagehide` 是浏览器能给的最好信号，且卸载期启动的音频常被丢弃 |

## 四、播放规则（照搬 pi-fairy）

- **优先级抢占**：`high(100) > medium(50) > low(10)`。新的音效优先级 **≥** 正在播的才打断；
  否则本次**直接丢弃**（不排队、不续播）。被中断的片段不恢复。
  - `high`：success / aborted / error / network-error / permission / compaction-failed / voice-*
  - `medium`：welcome / goodbye / new-session / session-switch / context-warning / quota-warning / compact-*
  - `low`：task-start / retry / model-switch / input / activity
- **同类不连播**：一个触发器有多段素材时随机选一段，且不与上一次相同。
- **冷却**：每个触发器有独立冷却窗（见 `lib/catalog.js` 的 `cooldownMs`），防止状态抖动连播。
- **静音**：`enabled=false` 或 `muted=true` 时全部不响 —— **除了 `voice-on` / `voice-off`**，
  它们必须响，否则你没法确认开关按下去生效了。

## 五、容错

每个信号源各自独立订阅、各自 `try/catch`：

- `ctx.inject(['sessions'])` / `(['remote'])` / `(['connection'])` 分开注册，
  宿主没有哪一个，只影响那一组触发器，插件不会整体哑掉。
- 订阅状态会显示在 设置 → Fairy 语音 → 状态区（「会话列表」「远程事件」「连接状态」「上下文占用」「余额」）。
  哪一条写着失败，就是那一路信号在这个宿主上不可用。
- 「复制诊断信息」把状态、最近触发记录、提示一起写进剪贴板，**不含任何对话内容**。

## 六、为什么不做朗读

原插件 `dsh-fairy-voice` 的整条链路是「把助手回复念出来」：
本地 GPT-SoVITS / MOSS-TTS 服务、流式 PCM 解码、语句切分、中文读音归一、长回答云端简报、9 项自检。
本插件把这条链路**整体删除**，因此也不存在这些失败模式：

- 没有「本机没跑 TTS 服务所以朗读按钮是灰的」
- 没有「参考音频不合格所以音色发毛」
- 没有「长回答被发去 `api.deepseek.com` 做简报」（原插件会把 ≥260 字的回复外发）
- 没有 `~/.dsh/fairy-voice/` 下的密钥文件
- 没有对 `@deepseek-ai/dsh-settings` 的版本 pin（上游在那个包的 `settingsNamespace` 存废上踩过坑）

浏览器只从**本机 DSH 服务**拉取 WAV，不发任何外部请求。
